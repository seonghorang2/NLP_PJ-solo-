# Review Insights Analysis Policy

## 1. 목적

이 문서는 `review-insights` 앱의 분석 정책을 정의한다.

이 문서의 목적은 다음과 같다.

- 전처리 기준을 명확하게 고정
- LLM 사용 범위를 제한
- 카테고리 분류 원칙을 일관되게 유지
- 주요 이슈 신호 집계 방식을 설명 가능하게 정의
- 결과 해석의 한계와 경고 규칙을 명시

이 문서는 구현 코드보다 상위의 분석 운영 기준 문서다.

---

## 2. 기본 원칙

- MVP 범위만 구현한다.
- 기본 분석은 결정론적 규칙 기반으로 수행한다.
- LLM은 애매한 리뷰에 대한 선택적 fallback으로만 사용한다.
- 원문 리뷰는 항상 보존한다.
- 분석 결과는 추적과 검토가 가능해야 한다.
- 단일 우선순위 점수는 MVP에서 사용하지 않는다.
- 이 서비스는 전체 유저 의견이 아니라 수집된 한국어 리뷰 표본을 분석한다.

---

## 3. 분석 대상 범위

이 앱은 다음 범위만 다룬다.

- 1개 또는 2개 게임
- Steam 리뷰
- 한국어 중심 리뷰 분석

이 앱은 다음을 하지 않는다.

- 추천 시스템
- 다국어 일반화 분석
- 대규모 ML 학습
- 전처리 전체의 블랙박스 자동화

---

## 4. 입력 데이터 정책

리뷰 단위에서 다음 메타데이터를 사용할 수 있다.

- `review_text`
- `voted_up`
- `timestamp_created`
- `timestamp_updated`
- `playtime_forever`
- `playtime_at_review_hours`
- `num_reviews`
- `appid`

정책:

- `playtime_at_review_hours`, `num_reviews`는 존재할 때만 사용한다.
- 값이 없으면 `null`을 허용한다.
- 이 필드들은 단일 점수 계산용이 아니라 해석 보조 신호로 사용한다.

---

## 5. 전처리 정책

전처리는 아래 순서를 따른다.

1. 공백 정리
2. 특수문자 및 반복문자 정리
3. 구문 중심 표현 정규화
4. 한글 비율 계산
5. 저품질 리뷰 판정
6. 욕설-only 판정
7. 애매한 리뷰 선별
8. 필요한 경우에만 LLM 보조 판정
9. 최종 포함/제외 결정
10. 판정 흔적 저장

---

## 6. 제외 정책

다음 리뷰는 분석에서 제외한다.

- 의미 없는 저품질 리뷰
- 단순 욕설-only 리뷰
- 주요 내용이 한국어가 아닌 리뷰

제외되더라도 메타데이터는 보존한다.

---

## 7. 한국어 판별 정책

한국어 판별은 한글 비율 기준으로 수행한다.

기준:

- 한글 범위: `[가-힣]`
- 전체 visible 문자 대비 한글 비율 계산

초기 기준 예시:

- `< 0.20`: 비한국어 가능성이 매우 높음
- `0.20 ~ 0.50`: 애매 구간
- `>= 0.50`: 한국어 중심으로 간주 가능

정책:

- 한글 비율이 매우 낮으면 제외 가능
- 경계 구간은 애매한 리뷰로 분류 가능
- 임계값은 고정 진리가 아니라 운영 중 조정 가능한 파라미터로 본다

---

## 8. 저품질 리뷰 정책

다음과 같은 리뷰는 저품질로 판단할 수 있다.

- 지나치게 짧은 리뷰
- 반복 문자 위주 리뷰
- 이모지 또는 기호-only 리뷰
- 정보성 단어가 거의 없는 리뷰

예:

- `ㅋㅋㅋ`
- `별로`
- `...`

정책:

- 저품질 판정은 보수적으로 적용한다.
- 짧더라도 구체적인 불만이나 칭찬이 있으면 포함 가능성을 열어둔다.

---

## 9. 욕설-only 정책

욕설이 포함되어 있다고 해서 자동 제외하지 않는다.

제외 기준:

- 욕설 또는 비난 표현만 있고
- 구체적인 피드백이나 주제 단서가 없는 경우

포함 기준:

- 욕설이 있더라도 구체적인 불만 또는 칭찬이 있는 경우

예:

- 제외: `쓰레기 게임`
- 포함: `쓰레기 같은 최적화 때문에 프레임이 계속 떨어짐`

---

## 10. 구문 중심 정규화 정책

단순 토큰화만으로는 한국어 게임 리뷰 표현 다양성을 충분히 흡수하기 어렵다.
따라서 전처리 단계에서 구문 중심 정규화를 우선한다.

예:

- `프레임 드랍`, `프레임드랍` -> `프레임드랍`
- `매칭 너무 오래 걸림`, `매칭이 안 잡힘` -> 대표 구문으로 통일 가능
- `최적화 별로`, `최적화 구림` -> 대표 표현으로 정규화 가능

정책:

- 원문은 보존한다.
- 정규화 결과는 별도 필드로 저장한다.
- 카테고리 분류는 토큰 추출보다 구문 사전과 대표 표현을 우선한다.

---

## 11. 애매한 리뷰 정책

애매한 리뷰는 규칙 기반만으로 확신 있게 판정하기 어려운 리뷰를 뜻한다.

예시 조건:

- 한글 비율이 경계 구간
- 욕설이 있으나 의미 있는 피드백 가능성 존재
- 반어, 비꼼, 우회 표현
- 비유적 표현
- 긍정과 부정이 혼재
- 카테고리 과다 매칭
- 키워드 사전에 거의 안 걸리지만 정보량은 있음

대표 플래그 예시:

- `ambiguous_language`
- `ambiguous_quality`
- `ambiguous_profanity`
- `ambiguous_sentiment`
- `ambiguous_category`
- `figurative_expression_detected`

---

## 12. LLM fallback 정책

LLM은 다음 역할에만 사용한다.

- 포함/제외 재판정
- 욕설-only와 유의미한 피드백 구분
- 반어, 비유, 문맥 해석
- 다중 카테고리 분류 보조
- 짧은 canonical theme 추출

LLM은 다음 역할에 사용하지 않는다.

- 원문 전체 재작성
- 전처리 전체 대체
- 근거 없는 자유 요약

운영 원칙:

- 전체 리뷰를 무차별 호출하지 않는다.
- 애매한 리뷰 subset에만 사용한다.
- 구조화된 JSON 출력만 허용한다.
- 규칙 기반 결과와 함께 저장한다.

---

## 13. 최종 판정 정책

최종 판정은 아래 원칙을 따른다.

- 명백한 규칙 기반 포함/제외는 그대로 채택한다.
- 애매한 리뷰만 LLM 호출을 고려한다.
- LLM은 보조 판정기로만 사용한다.
- 규칙 기반, LLM 기반, 최종 판정 흔적을 모두 저장한다.

권장 필드:

- `rule_decision`
- `llm_invoked`
- `llm_decision`
- `llm_confidence`
- `final_decision_source`
- `included_in_analysis`

---

## 14. 카테고리 분류 정책

카테고리 분류는 규칙 기반 매핑을 기본으로 한다.

초기 카테고리:

- `bugs`
- `performance`
- `balance`
- `story`
- `graphics`
- `monetization`
- `multiplayer`
- `localization`
- `difficulty`
- `controls`

정책:

- 하나의 리뷰가 여러 카테고리에 동시에 속할 수 있다.
- 카테고리 집계는 리뷰 수가 아니라 이슈 언급 수 개념으로 본다.
- `primary_category`는 필요 시 보조 필드로만 사용한다.

---

## 15. 키워드 및 테마 추출 정책

테마 추출은 unigram-only 접근으로 고정하지 않는다.

우선 순위:

1. 대표 구문
2. 짧은 phrase 또는 bigram
3. 대표 키워드
4. 필요한 경우 canonical theme 보조

정책:

- 긍정 리뷰와 부정 리뷰를 분리한다.
- 카테고리별 집계를 우선한다.
- canonical theme은 원문을 대체하지 않고 해석 보조로만 사용한다.

---

## 16. 주요 이슈 신호 정책

MVP에서는 단일 우선순위 점수를 계산하지 않는다.

대신 다음과 같은 `주요 이슈 신호`를 카테고리별로 제공한다.

- `mention_count`
- `negative_ratio`
- `recent_trend`
- `experienced_player_share`
- `themes`
- `sample_reviews`

정책:

- 하나의 숫자로 문제 중요도를 단정하지 않는다.
- 최종 우선순위 판단은 사람이 수행한다.
- 대시보드에서는 신호와 대표 리뷰를 함께 보여준다.

---

## 17. 표본 대표성 및 해석 제한 정책

이 서비스는 `전체 유저 의견`이 아니라 `수집된 한국어 리뷰 표본`을 분석한다.

따라서 모든 결과는 다음 원칙 아래에서 해석해야 한다.

- 분석 결과를 시장 전체 반응으로 일반화하지 않는다.
- 리뷰를 남기지 않은 유저의 의견은 포함되지 않는다.
- 특히 리뷰 수가 적은 게임에서는 소수 의견이 과대표집될 수 있다.
- 대시보드, 요약, 비교 결과 모두 이 한계를 숨기지 않는다.

이 정책은 트렌드 분석, 주요 이슈 신호, 게임 간 비교, 요약 생성 전반에 동일하게 적용한다.

---

## 18. 표본 충분성 등급 정책

게임별 분석 포함 리뷰 수를 기준으로 표본 충분성 등급을 부여한다.

- `very_small`: 1~29
- `small`: 30~99
- `medium`: 100~499
- `large`: 500+

정책:

- `sample_size_tier`는 분석 결과와 함께 저장 가능하게 설계한다.
- 표본 등급이 낮을수록 결과를 더 약하게 표현한다.

등급별 해석 규칙:

### `very_small`

- 카테고리 언급, 대표 키워드, 대표 리뷰는 표시 가능
- 트렌드 해석은 기본적으로 제한
- 게임 간 직접 비교는 비권장 또는 제한
- 요약에 강한 주의 문구 삽입

### `small`

- 기본 분석 허용
- 트렌드는 약한 신호로만 표시
- 비교 결과에 주의 문구 삽입
- 단정형 문장보다 조건형 문장 우선

### `medium`

- 일반적인 트렌드 해석 허용
- 비교 기능 허용 가능
- 비교 조건이 맞지 않으면 경고 유지

### `large`

- 일반 분석, 트렌드, 비교를 허용할 수 있음
- 그래도 표본 기반 신호라는 점은 유지

---

## 19. 트렌드 분석 정책

트렌드는 주 단위 집계를 기본으로 한다.

기본 집계:

- 주차별 카테고리 언급 수
- 최근 4주 vs 이전 4주 비교

초기 규칙 예시:

- `recent_count >= 5`
- `recent_count >= prior_count * 1.5`

정책:

- 최근 기간과 이전 기간 모두 최소 리뷰 수를 충족해야 한다.
- 비율 변화만으로 급증 또는 급감을 판정하지 않는다.
- `최소 절대 증가량`과 `최소 리뷰 수`를 함께 충족해야 강한 추세 신호를 표시한다.
- 모수가 작은 경우 트렌드 상태를 `limited` 또는 `unstable`로 표시한다.
- 리뷰 수가 매우 적은 경우 1건에서 2건으로의 변화는 강한 급증으로 해석하지 않는다.

권장 필드:

- `trend_status`
- `trend_reason`
- `recent_window_review_count`
- `previous_window_review_count`

---

## 20. 비교 가능성 정책

게임 간 비교는 항상 허용하지 않는다.

비교 전에는 다음 조건을 함께 고려한다.

- 장르 유사성
- 가격 모델 유사성
- 출시 단계 유사성
- 리뷰 규모 차이
- 비교 기간 정렬 여부

비교 상태:

- `comparable`
- `compare_with_caution`
- `not_comparable`

### `comparable`

다음 조건이 대체로 충족될 때 사용한다.

- 장르가 유사하다
- 가격 모델이 크게 다르지 않다
- 출시 단계가 유사하다
- 분석 포함 리뷰 수 차이가 과도하지 않다
- 비교 기간이 정렬되어 있다

### `compare_with_caution`

다음과 같은 경우 사용한다.

- 장르는 유사하지만 리뷰 규모 차이가 크다
- 비교 기간은 맞지만 출시 단계 차이가 있다
- 장르 또는 가격 모델 차이가 일부 존재한다

이 경우 비교는 허용할 수 있지만, 해석 주의 문구를 반드시 포함한다.

### `not_comparable`

다음과 같은 경우 사용한다.

- 출시 초기 게임과 장기 운영 게임을 직접 비교하는 경우
- 얼리액세스 게임과 정식 출시 장기 게임을 비교하는 경우
- 한쪽 게임의 표본이 매우 작아 비교가 불안정한 경우
- 비교 기간이 정렬되지 않은 경우
- 게임 성격 차이가 너무 커 직접 비교가 부적절한 경우

이 상태에서는 직접 비교 결과를 제한하거나 비활성화한다.

권장 필드:

- `comparison_status`
- `comparison_reason`
- `comparison_warnings`

---

## 21. 시간축 정렬 정책

게임 비교와 트렌드 해석에서는 시간축을 명확히 구분한다.

두 가지 비교 방식을 사용한다.

- `calendar_aligned`
  - 같은 실제 기간을 비교
- `lifecycle_aligned`
  - 출시 후 경과 주차 기준으로 비교

정책:

- 출시 초기 반응 비교에는 `lifecycle_aligned`를 우선 고려한다.
- 패치 전후 비교에는 동일 이벤트 기준 기간을 사용한다.
- 달력 기간만 맞춘 비교가 제품 상태 비교로 오해되지 않게 한다.

---

## 22. 플레이타임 세그먼트 정책

MVP에서는 두 개의 세그먼트만 둔다.

- `new_players`
- `experienced_players`

초기 기준 예시:

- `< 120분` -> `new_players`
- `>= 120분` -> `experienced_players`

이 기준은 운영 중 조정 가능하다.

---

## 23. 결과 표시 정책

대시보드는 다음을 명시해야 한다.

- 총 분석 리뷰 수
- 필터링된 리뷰 수
- 카테고리별 언급 수
- 주요 이슈 신호
- 대표 리뷰 예시

정책:

- 비율만 단독으로 보여주지 않는다.
- 비율과 함께 분모 또는 리뷰 수를 함께 표시한다.
- 작은 표본에는 `표본 작음`, `해석 주의`, `비교 주의` 라벨을 붙인다.
- 카테고리 합계가 전체 리뷰 수와 같아 보이게 만들지 않는다.
- 주요 이슈 신호는 점수나 자동 우선순위가 아니라 해석용 근거임을 명시한다.

예:

- `부정 비율 80% (4/5)`
- `performance 언급 증가, 최근 표본 작음`
- `비교 주의: 출시 단계 차이 존재`

---

## 24. 요약 생성 정책

요약은 사용자가 가장 쉽게 과신하는 출력이므로 가장 보수적으로 생성한다.

금지 표현:

- `전체 유저들은`
- `시장은 전반적으로`
- `플레이어들은 대체로`
- `이 게임은 확실히`

권장 표현:

- `현재 수집된 한국어 리뷰 기준`
- `분석 포함 리뷰 표본에서 반복적으로 나타난 신호는`
- `표본이 작아 해석에 주의가 필요하지만`
- `최근 리뷰 표본에서는`

정책:

- 표본 등급이 작을수록 단정형 문장을 줄인다.
- 조건형 문장을 우선 사용한다.
- 결과의 한계를 숨기지 않는다.

---

## 25. 경고 문구 정책

대시보드와 요약에는 상황에 따라 아래 문구를 포함할 수 있어야 한다.

### 공통

- `이 결과는 수집된 한국어 리뷰 표본을 기준으로 합니다.`
- `전체 유저 의견을 대표하지 않을 수 있습니다.`

### 표본이 작은 경우

- `분석 포함 리뷰 수가 적어 해석에 주의가 필요합니다.`
- `현재 표본이 작아 트렌드와 테마 신호가 불안정할 수 있습니다.`

### 트렌드 제한 시

- `최근 리뷰 수가 적어 추세 해석이 제한됩니다.`
- `표본이 작아 급증/급감 신호를 표시하지 않습니다.`

### 비교 주의 시

- `두 게임의 출시 단계 또는 리뷰 규모 차이로 인해 직접 비교에 주의가 필요합니다.`
- `이 비교는 리뷰 패턴 차이를 보여주며, 품질 우열을 의미하지 않습니다.`

### 비교 제한 시

- `두 게임은 현재 조건에서 직접 비교에 적합하지 않습니다.`
- `장르, 출시 단계, 또는 표본 규모 차이로 인해 비교 결과를 제공하지 않습니다.`

## 26. 권장 결과 필드

이 정책을 지원하기 위해 분석 결과에는 아래 필드를 함께 둘 수 있다.

```json
{
  "sample_size_tier": "small",
  "trend_status": "limited",
  "trend_reason": "insufficient_recent_volume",
  "comparison_status": "compare_with_caution",
  "comparison_reason": "release_stage_mismatch",
  "warnings": [

    "분석 포함 리뷰 수가 적어 해석에 주의가 필요합니다."
  ]
}
```

권장 필드:

- `sample_size_tier`
- `trend_status`
- `trend_reason`
- `comparison_status`
- `comparison_reason`
- `warnings`

## 29. 운영 원칙

이 정책의 목적은 결과를 더 많이 생성하는 것이 아니라,
과신을 막고 해석 책임을 명확히 하는 것이다.

따라서 아래 원칙을 유지한다.

- 표본이 작을수록 결과를 약하게 말한다.
- 비교 조건이 맞지 않으면 비교를 제한한다.
- 트렌드가 불안정하면 경고하거나 숨긴다.
- 사용자가 결과의 근거와 한계를 동시에 볼 수 있게 한다.
